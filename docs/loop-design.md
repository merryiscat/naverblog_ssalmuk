# 루프 설계 — 자가 보정의 구조와 판단 기준

> derived_from: 대화 2026-08-17 (사용자 확정: Phase 0 = 4주, 탐색:활용 = 1:1).
> C5(일일 보정)·C4(측정)·스케줄러의 구현 사양. 근거는 [mate-analysis.md](mate-analysis.md).

## 3겹 루프 — 주기가 다른 결정은 다른 루프에서만

| 루프 | 주기 | 담당 | 바꿀 수 있는 것 |
|------|------|------|----------------|
| 일일 (운영) | 매일 | 주제 발굴→생성·게이트→발행→측정→야간 보정→리포트 | 오늘의 주제 선택, 템플릿 선택, 발행 시각 |
| 주간 (전략) | 주 1회 | 경쟁·공백 관찰(C6) + 글 유형별 성과 집계 → 실험 평가 | 시드 구성, 주제 유형 비중, 실험 계획 |
| 월간 (프로그램) | 월 1회 | 선정자 리스트 수집(C7) → 커트라인·기준 변화 감지 | 분야 전략(target_categories), 국면 전환 검토 |

전권 위임이지만 **결정의 주기는 루프의 주기를 넘을 수 없다** — 일일 보정이 시드를 갈아엎는 일은 구조적으로 불가능하게 한다. 이것이 결정 진동의 1차 방어선.

## 에이전트 공통 원칙 — 고민 → 검토 → 실행 → 복기

> derived_from: 대화 2026-08-19 (사용자 확정). 모든 에이전트(왕복 루프·메이트 관찰·블로그 검수·이후 추가분)의 공통 뼈대.

| 단계 | 뜻 | 구현 장치 |
|------|-----|----------|
| **고민** | 계속해서 뭘 할지 스스로 정한다 | 탐색 재량 (메이트 관찰의 도구 선택, 검수의 대상 선정, 게이트의 action 지시) |
| **검토** | 실행해도 괜찮은지 먼저 심사한다 | 가드레일 ①~④ + 예산(도구 호출 상한·월 비용) + C5 검증기(냉각기·Phase 제약). 읽기 전용 작업은 통과, 상태를 바꾸는 작업일수록 심사가 두꺼워진다 |
| **실행** | 문제없으면 실행한다 | 각 에이전트 본체 |
| **복기** | 실행 결과를 돌아보고 다음에 반영한다 | 검수의 resolved/persisting 추적(지난 지적 재확인), decisions 로그(rationale 필수), 게이트 피드백 재작성 루프, C4 측정→C5 보정 |

새 에이전트를 설계할 때 이 4단계가 어디에 있는지 명시한다 — 하나라도 비면 (특히 복기)
"실행만 하고 배우지 않는" 자동화가 된다. 2026-08-18 신선도 사고가 그 사례:
실행(발행)은 됐지만 결과를 화면으로 복기하는 장치가 없어 사람이 발견할 때까지 몰랐다.

### 검수 2갈래 — 정기 점검 vs 신규 발굴 (2026-08-21 사용자 지시)

검수 에이전트는 두 갈래로 본다:

| 갈래 | 내용 | 장치 |
|------|------|------|
| **A. 정기 점검** | 알려진 실패 유형을 매회 pass/fail **회귀 판정** (렌더링, 각주, 신선도 표기, 카테고리 매칭, 이미지, 썸네일 다양성, 프로필 정합, 표 가독성) | inspector.py `REGULAR_CHECKS` 목록. 기계 대조 가능한 항목은 코드 체크 병행(카테고리 — DOM vs DB). 실패는 텔레그램에 "📋 정기 실패"로 최우선 표시 |
| **B. 신규 발굴** | A에 없는 문제를 심사자·독자 눈으로 탐색 (A 재탕 금지, 억지 발굴 금지) | 프롬프트 B절. 발굴은 복기(resolved/persisting) 추적 대상 |

**승격 규칙**: B의 발굴이 **2회 반복(persisting)되거나 실사고로 확인**되면
REGULAR_CHECKS에 항목을 추가한다(코드 수정) — 목록이 사고에서 배우며 자란다.
카테고리 오배정(08-21)이 이 규칙의 기원: "그 외 모든 것"에 묻혀 발굴되지 못한
알려진 유형은 체크리스트로 고정해야 다시는 안 놓친다.

### 검수 오케스트레이터 체인 (2026-08-21 추가, 사용자 위임)

검수 의견을 "사용자 결정 대기"로 쌓지 않는다 — 검수(의견) → 오케스트레이터(결정) →
수행 에이전트(실행)의 3자 체인이 처리하고 사람은 결과 보고만 받는다.

| 단계 | 담당 | 장치 |
|------|------|------|
| 고민 | orchestrator.py (gpt-5.4) | 검수 보고 + 현재 설정 + 최근 발행 글로 판단 |
| 검토 | 코드 가드 | 화이트리스트 5액션 + 값 제약 검증, 정체성 항목(블로그명·별명) 14일 1회, 카탈로그 밖은 manual 분류(실행 불가 구조) |
| 실행 | blog_actions.py | 대상 페이지 재검증 → 반영 → **재조회로 실반영 확인** |
| 복기 | decisions 기록 | 직전 결정을 성공/실패 구분해 다음 판단에 입력 — 성공 항목 재변경만 진동으로 간주 |

## 계기판 — 시차가 다른 3단 지표

| 단계 | 지표 | 시차 | 비고 |
|------|------|------|------|
| **선행 (초기 1차 신호)** | **글별 ai_cited** (타깃 쿼리의 브리핑 출처에 내 글 등장), 검색 노출 순위, 방문·유입 키워드, 대상 쿼리의 브리핑 유무·출처 신선도 | 1~7일 | 프로필 인용수가 100 미만 구간에서 침묵하므로 이게 실질 계기판 |
| 핵심 | 프로필 인용수 (누적/당월 — 매일 갱신, 100 미만은 뭉뚱그림) | 수 주 | 100 돌파 후부터 유의미 |
| 최종 | 메이트 선정 여부 | **+2개월** | 선정은 2개월 전 월간 인용수 기준 (실측 확정) |

**타임라인 기대치**: 8월 말 발행 시작 → 첫 인용 9~10월 (가정) → 반영 선정 11~12월.
첫 선정 평가는 11월 이전에 하지 않는다 (조기 비관 금지).

## 국면(Phase) — 콜드 스타트 규칙

- **Phase 0 — 탐색** (발행 개시 후 **4주** 또는 첫 ai_cited 중 빠른 쪽): 여러 분야 분산 발행.
  보정은 일일 주제 선택만. **전략 변경 금지** (관찰 축적 모드). 선행 지표만 수집.
- **Phase 1 — 가중**: 신호(ai_cited·노출 상위·유입)가 나온 분야·글 유형에 발행 비중 이동.
- **Phase 2 — 수렴**: `target_categories`로 1~2개 분야 집중 (C-rank 공식 근거).

**전환 조건은 규칙으로**: Phase 0→1 = 첫 ai_cited 발생 또는 4주 경과. Phase 1→2 = 동일 분야
ai_cited 2회 이상. 전환은 주간 루프에서만 판정. LLM의 재량이 아니라 데이터 조건이 국면을 바꾼다.

## 일일 보정의 판단 규칙

1. **탐색:활용 = 1:1** — 일 3건(2026-08-21 상향)이면 활용 1~2 + 탐색 1~2. Phase 0에서는 전건 탐색(분야 분산).
2. **한 번에 한 변수** — 템플릿 변형 / 발행 시각 / 주제 유형 중 하루 하나만 실험.
3. **평가 유예** — 글은 발행 +7일 후 선행 지표로 평가, 인용 귀속은 +4주 유예. 유예 전 데이터로 결정 금지.
4. **변경 냉각기** — 같은 결정 항목은 주 1회만 변경. 동일 항목 3회 번복 감지 시 소환 알림.
5. **하드 가드레일 불변** — 일 발행 ≤4(2026-08-21 사용자 상향, 기본 3+α) / 월 3만원 정지 / 상호작용 자동화 금지 / 게이트 미달 발행 금지.

## 루프 = 레퍼런스 수집 장치

Phase 0의 분산 발행이 문헌에 없는 데이터(신규 블로그 첫 인용까지 기간, 글 유형별 승률)를 직접
생산한다. 주간 집계는 [mate-analysis.md](mate-analysis.md)에 실측 절로 누적한다 — 분석 문서가
운영 데이터로 계속 자라는 구조.

## 공통 전제 — 여러 케이스가 같이 밟는 토대

1. **네이버 세션 인프라** — Playwright storage_state 저장·만료 감지·자동 재로그인(tokbiseo 3단 방어 이식). 발행·측정·경쟁 관찰이 공용. 캡차·기기확인 등 자동화 불가 상황이면 텔레그램 소환.
2. **SQLite 저장소** — 키워드 관찰치, 발행 이력, 측정치(인용수·순위), 보정 결정 로그, 비용 원장.
3. **텔레그램 봇** — 일일 리포트, 이상 알림, 소환. 수신 전용이 기본(완전 방치), 정지/재개 명령 정도만 수신.
4. **LLM 호출 계층 + 비용 미터링** — 모든 OpenAI 호출이 한 게이트웨이를 지나 비용을 SQLite에 적산. 월 3만원 도달 시 파이프라인 자동 정지 + 알림.
5. **스케줄러** — 미니PC 상주 프로세스(APScheduler류). 발행·측정 시각을 사람 같은 패턴으로 분산(랜덤 지터).
6. **보정 정책 저장소** — 시스템이 매일 갱신하는 "현재 방향"(주제 풀, 템플릿 선택, 실험 중 가설)과 결정 로그. 전권 위임이므로 **왜 바꿨는지**가 반드시 남아야 한다.

### C0. 셋업 위저드 (최초 1회, 사용자 동석)

**해피 패스 (대본)**
1. 사용자가 `uv run setup` 실행 → 위저드가 체크리스트 표시 (P1~P9 상태).
2. "네이버 로그인을 시작합니다" → Playwright 브라우저가 뜨고 사용자가 직접 ID/PW·2단계 인증 입력 → 위저드가 storage_state 저장 → "세션 저장 완료, 유효성 검사 통과".
3. "블로그 관리 > AI 활용 설정 페이지를 엽니다" → 사용자가 ON 클릭 → 위저드가 설정 상태를 읽어 확인.
4. 검색광고 API·오픈API·텔레그램 봇 발급 절차를 단계별 안내(URL 열어주기 + 키 입력받아 .env 저장 + 즉석 호출 테스트).
5. 프로필 인용수 UI를 열어 실제 위치·형식을 확인하고 셀렉터를 기록 (P8 검증).
6. 메이트 선정자 목록 공개 여부를 같이 확인 (P9) → 결과를 pending.md에 반영.
7. 완료 신호: 체크리스트 전 항목 ✅ + "첫 파이프라인 실행을 예약했습니다" 메시지 + 텔레그램으로 테스트 알림 도착.

**배드 케이스**
| 상황 | 대응 |
|------|------|
| 캡차·기기확인으로 로그인 실패 | 막지 않고 사용자가 브라우저에서 직접 해결할 때까지 대기 (동석 전제라 가능) |
| 검색광고 광고주 가입 반려·지연 | 알리고 넘어감 — P4 없이 C1을 상대 지표 모드(데이터랩만)로 임시 가동, P4 확보 시 승격 |
| 인용수 UI가 소문과 다름 (P8 실패) | 측정 1차 지표를 재설계해야 하므로 **막음** — 사용자와 대안 논의 후 진행 |

**필요 기술** — Playwright(수동 개입 허용 모드), .env 관리, API 즉석 검증 호출, 체크리스트 상태 저장(SQLite)

### C1. 주제 발굴 (매일 새벽)

**해피 패스 (대본)**
1. 스케줄러가 새벽 3~5시 사이 랜덤 시각에 기동.
2. 데이터랩 트렌드 + 검색광고 월간 검색량 + 자동완성·연관검색으로 후보 키워드 ~50개 수집.
3. 각 후보에 골든키워드 점수(검색량÷문서수) 계산 → 상위권을 LLM 선제 스코어링("쓸 가치 있나·경쟁 강도·보정 정책의 현재 방향과 맞나")으로 재정렬.
4. 발행 이력과 대조해 중복·유사 주제 제외 → 오늘의 주제 1~2개 + 예비 1개 확정, SQLite 기록.
5. 완료 신호: `topics` 테이블에 오늘 날짜 행 + 선정 근거(점수·판단 로그)가 남아 있다.

**배드 케이스**
| 상황 | 대응 |
|------|------|
| API 쿼터 초과·장애 | 되돌림 — 전일 캐시로 후보 구성, 리포트에 "캐시 모드" 명시 |
| 후보 전부 저점수 (쓸 만한 게 0건) | 알리고 넘어감 — 그날 발행 스킵 (억지 주제 금지), 사유 리포트 |
| 검색광고 API 미확보(P4 대기) | 상대 지표 모드로 강등 운영 |

**필요 기술** — 검색광고 API(월간 검색량·연관키워드 — **주 소스**), **검색 API(기존 앱 재활용 — 문서수 집계)**, 자동완성 스크래핑, 데이터랩 웹 저볼륨 스크래핑(상대 트렌드 — 데이터랩 API 추가 성공 시 API로 대체), 점수화 로직, LLM 판단 호출(gpt-5.4-mini급)
※ 오픈API 신규 발급은 2026-08 중단 확인 — P3 참조. 검색 API 재활용 확정으로 스크래핑 의존도가 당초 우려보다 낮아짐 (측정 C4의 순위 확인도 검색 API로 가능).

### C2. 글 생성 + 이미지 (매일)

**해피 패스 (대본)**
1. 주제를 받아 웹 리서치(검색→본문 수집→사실 추출, 출처 URL 보존).
2. GEO 구조 템플릿(H2/H3 위계, 표·목록, FAQ, 발행일 명시)으로 정보 정리·분석형 초안 작성 — 보정 정책이 지정한 템플릿 사용.
3. 품질 게이트 채점: 사실성(출처 대조), 去AI味(AI 티 제거), GEO 체크리스트, 중복도. 불합격 항목은 피드백으로 재생성 (최대 2회).
4. 글 성격에 따라 이미지 생성 — 정보형: 데이터 기반 차트·요약카드(matplotlib/HTML 렌더), 비주얼 주제: OpenAI 이미지 API. 썸네일 1 + 본문 2~3장.
5. 완료 신호: `posts` 테이블에 초안 상태 행 + 본문 파일 + 이미지 파일 + 게이트 점수 기록.

**배드 케이스**
| 상황 | 대응 |
|------|------|
| 리서치 결과 빈약 (신뢰할 출처 <3) | 되돌림 — 주제 폐기, 예비 주제로 교체 1회, 그것도 실패면 그날 스킵 |
| 게이트 재생성 2회도 실패 | **그날 발행 스킵** (확정 정책) — 실패 원인 리포트, 보정 재료화 |
| LLM API 장애 | 재시도 백오프 → 지속 시 그날 스킵 + 알림 |
| 이미지 생성 실패 | 알리고 넘어감 — 텍스트만으로 발행 (이미지는 필수 아님) |
| 비용 상한 근접 | 이미지 생성 생략 → 상한 도달 시 전체 정지 (공통 가드레일) |

**필요 기술** — 웹 검색·본문 추출, LLM 작문(gpt-4.1 계열)+판단(gpt-5.4-mini), 去AI味 게이트, matplotlib/HTML→이미지 렌더링, OpenAI 이미지 API

### C3. 발행 (매일 1~2회, 시각 분산)

**해피 패스 (대본)**
1. 보정 정책이 정한 발행 시각(사람 같은 시간대, 일정 지터)에 세션 로드 → 유효성 확인.
2. 스마트에디터 ONE을 Playwright로 조작 — 제목·본문 블록·이미지 업로드·카테고리·태그 입력.
3. 발행 클릭 → **발행 성공을 믿지 않고** 공개 URL을 비로그인 컨텍스트로 열어 실게시 확인 (知乎 '가짜 성공' 함정 대응).
4. 완료 신호: `posts` 행이 발행 상태 + 공개 URL + 실게시 확인 타임스탬프.

**배드 케이스**
| 상황 | 대응 |
|------|------|
| 세션 만료 | 자동 재로그인 3단 방어 → 실패 시 파이프라인 일시정지 + 텔레그램 소환 |
| 캡차·기기확인 발생 | 막음 + 소환 — 완전 방치의 유일한 예외 지점 |
| 에디터 셀렉터 깨짐 (UI 개편) | 실패 감지 + 스크린샷 첨부 알림, 그날 발행 중단 (임시저장 시도 후) |
| 발행됐는데 실게시 확인 실패 | 알림 + 수동 확인 요청 — 중복 발행 방지 위해 재시도 금지 |
| 일 2건 상한 도달 | 하드 가드레일 — 코드가 차단 |

**필요 기술** — Playwright + storage_state(공통 전제 1), 스마트에디터 ONE 셀렉터 모듈(space-cap/konamgil 참고), 발행 후 검증, 스크린샷 캡처

### C4. 측정 (매일)

**해피 패스 (대본)**
1. 로그인 세션으로 내 프로필 인용수 확인(2026-06부터 제공되는 UI, 셀렉터는 C0에서 확보) → 일별 스냅샷 저장.
2. 발행 글의 타깃 키워드로 네이버 검색 → 내 글의 노출 순위·AI 브리핑 인용 여부 기록 (쿼리 수 최소화, 지터).
3. 블로그 방문자·유입 키워드 통계(크리에이터 어드바이저) 수집.
4. 완료 신호: `metrics` 테이블에 오늘 스냅샷, 전일 대비 증감 계산됨.

**배드 케이스**
| 상황 | 대응 |
|------|------|
| 인용수 UI 변경·접근 실패 | 알리고 넘어감 — 마지막 값 유지 + 측정 공백 플래그, 3일 연속이면 소환 |
| 검색 스크래핑 봇 감지·차단 | 되돌림 — 쿼리 볼륨 절반으로 축소 + 백오프, 지속 시 순위 측정 잠정 중단(인용수만 유지) |
| 측정치 급락 (저품질 의심 신호) | 알림 격상 — 보정 노드에 최우선 전달 |

**필요 기술** — Playwright(로그인 컨텍스트), 검색 결과 파싱, 시계열 저장·증감 계산

### C5. 일일 자가 보정 + 리포트 (매일 밤)

**해피 패스 (대본)**
1. 그날의 측정치·발행 결과·게이트 통과율·경쟁 관찰 요약을 모아 LLM(gpt-5.4급)에 투입.
2. LLM이 방향 결정 — 주제 풀 조정, 키워드 우선순위, 템플릿 선택, 카테고리 전환, 실험 가설 설정("이번 주는 FAQ형 vs 비교표형 비교") 등 **전권 범위 내에서**. 하드 가드레일 항목은 제안만 가능(변경 불가).
3. 결정과 근거를 `decisions` 로그에 기록, 보정 정책 저장소 갱신.
4. 텔레그램 일일 리포트 발송: 오늘 발행(제목·URL) / 측정 증감 / **오늘의 보정 내용과 이유** / 비용 누계 / 이상 신호.
5. 완료 신호: 리포트 수신 + decisions 행 + 다음 날 파이프라인이 갱신된 정책을 읽는다.

**배드 케이스**
| 상황 | 대응 |
|------|------|
| 보정 LLM이 가드레일 밖 결정 시도 | 막음 — 정책 검증기가 거부, 거부 사실을 리포트에 |
| 데이터 부족 (초기 몇 주, 인용 0) | 알리고 넘어감 — "관찰 축적 모드" 명시, 무리한 방향 전환 억제 규칙 |
| 텔레그램 발송 실패 | 재시도 → 로컬 로그 보존 (리포트 유실돼도 파이프라인은 계속) |
| 연속 성과 정체로 극단 결정 반복 | 결정 진동 감지(같은 항목 3회 이상 번복 시) → 소환 알림 |

**필요 기술** — LLM 판단 호출(최상위 모델), 정책 스키마+검증기, 텔레그램 발송, 결정 로그

### C6. 경쟁 블로그 관찰 (주 1~2회)

**해피 패스 (대본)**
1. 내 주제 풀의 키워드로 네이버 검색 → AI 브리핑에 인용된 출처 블로그·글 URL 수집.
2. 인용된 글의 구조(헤딩 위계·표·FAQ·글자수·이미지 수·발행일)를 파싱해 패턴 축적.
3. 내 글과 구조 비교 → 차이점을 보정 노드(C5)의 입력으로 전달.
4. 완료 신호: `competitors` 테이블 갱신 + 주간 패턴 요약이 보정 입력에 포함됨.

**배드 케이스**
| 상황 | 대응 |
|------|------|
| AI 브리핑 미노출 키워드 (관찰 대상 없음) | 알리고 넘어감 — "이 키워드는 AI 브리핑 자체가 안 뜸"도 주제 선정에 유용한 신호로 기록 |
| 봇 차단 (네이버가 외부 크롤링 차단 중) | 되돌림 — 주기·볼륨 축소, 로그인 세션 재사용, 지속 실패 시 기능 잠정 중단 (코어에 영향 없게 격리) |

**필요 기술** — 검색 결과·AI 브리핑 파싱, 블로그 본문 구조 분석, 패턴 저장

## 기술 요구 집계 (3부 재료 — 케이스 밖으로 꺼낸 중복 제거 목록)

**외부 의존**: 네이버 계정+블로그(AI 활용 ON), 네이버 오픈API 키, 검색광고 API 광고주 계정, OpenAI API 키, 텔레그램 봇 토큰, 상시 ON 미니PC(Windows)

**라이브러리·런타임**: Python+uv, Playwright(발행·측정·관찰 공용 세션), SQLite, APScheduler류 상주 스케줄러, matplotlib/HTML→이미지 렌더, python-telegram-bot류, OpenAI SDK

**기술 난제**:
1. 스마트에디터 ONE 자동 조작의 내구성 (셀렉터 깨짐 감지·복구 체계)
2. 네이버 봇 감지 회피가 아닌 **감지 안 당할 만큼만 관찰하는** 쿼리 예산 설계 (측정·경쟁 관찰)
3. 자가 보정의 안전한 전권 위임 — 정책 스키마 + 검증기 + 결정 진동 감지
4. 비용 적산·자동 정지의 정확성 (모든 LLM·이미지 호출 단일 게이트웨이 강제)
5. 발행 '가짜 성공' 방지 — 비로그인 실게시 검증
